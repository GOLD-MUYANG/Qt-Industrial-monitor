## 1. 文档信息

| 项目 | 内容 |

## 2. 项目目标

本项目实现一套可以在单机上完整演示的工业设备监控系统。当前包含 VirtualPLC、
Widgets/QML 两个互斥的上位机入口、一个动态协议插件，以及 Widgets 入口中的独立
OpenCV 视觉实验模块：

```text
VirtualPLC
    |
    | Modbus TCP
    v
IndustrialMonitor
    |
    +-- 实时展示
    +-- 状态统计
    +-- 阈值报警
    +-- SQLite 存储
    +-- OpenCV 视觉实验（Widgets 独立支线）
```

项目重点不是模拟大型 SCADA 平台，而是完成一条可运行、可测试、可解释的工业数据链路：

```text
发现协议插件 -> 建立连接 -> 周期采集 -> 数据解析
-> 数据质量判断 -> 实时统计 -> 报警判断 -> SQLite 持久化
-> 实时界面与历史查询 -> 断线重连
```

完成后，演示者应当能够从源码解释每个数据对象由谁创建、在哪个线程使用、如何跨模块传递，以及失败时如何恢复。

## 3. 首版范围

### 3.1 必须实现

- `IndustrialMonitor` Qt Widgets 上位机。
- `VirtualPLC` Qt Widgets 模拟设备。
- 使用 `QPluginLoader` 动态加载 Modbus TCP 协议插件。
- 使用 `QModbusTcpClient` 异步读取和写入寄存器。
- 使用 `QModbusTcpServer` 模拟 PLC。
- 采集温度、压力、转速、电压和运行状态。
- 默认每 500 ms 采集一次，且同一设备最多只有一个读请求在途。
- 展示当前值、最近 60 秒最大值、最小值和平均值。
- 展示最近 60 秒实时曲线，支持暂停和恢复显示。
- 实现阈值报警、报警确认、报警恢复和历史查询。
- 实现连接状态机、超时、错误计数和自动重连。
- 使用 SQLite 保存设备、测点、测量值、报警规则和报警事件。
- 支持按设备、测点和时间范围查询历史数据（后端查询 Worker 已实现，完整页面待实现）。
- 支持 CSV 导出（规划项，当前未实现）。
- 记录逻辑层通信日志，包括功能码、地址、数量、耗时和错误（页面与文件滚动待实现）。
- VirtualPLC 支持自动变化、制造高温报警、断开通信和恢复通信。
- 使用 CTest 组织单元测试和集成测试。
- 提供 `industrial_monitor_qml` 并行前端，共用同一个应用控制器和业务后端。
- Widgets 提供独立“视觉实验”页，支持本地视频播放和固定 HSV 红色目标检测。

### 3.2 明确不做

- Modbus RTU、普通 TCP、UDP 和裸串口通信。
- 协议插件运行时热卸载或无停机升级。
- 完整 Modbus TCP MBAP 报文抓包和原始 HEX 调试器。
- 配方管理、用户权限、远程部署和多机集群。
- PLC 厂商私有协议和真实硬件认证。
- 脚本系统、插件市场和通用工作流引擎。
- 为了展示技术而引入额外线程、消息中间件或依赖注入框架。
- 摄像头采集、AI/YOLO/通用目标识别和生产级视觉质检。
- 将视觉计数写入 Modbus、报警或 SQLite；保存检测视频或截图。

以上能力可作为后续扩展，但不能阻塞首版闭环。

## 4. 技术选择

| 能力 | 技术选择 | 选择原因 |
| --- | --- | --- |
| 桌面界面 | Qt Widgets | 与当前学习目标和桌面上位机场景一致 |
| 并行前端 | Qt Quick / QML | 验证同一业务后端可被另一套展示层复用 |
| 构建系统 | CMake 3.22+ | 当前环境可用，便于组织多个目标与测试 |
| Modbus | Qt Serial Bus | 提供异步 Client、Server、超时和重试机制 |
| 动态插件 | Qt Plugin System | 原生支持接口声明、元数据和运行时加载 |
| 实时曲线 | Qt Charts | 兼容当前 Qt 6.2.4；不以更新版本 Qt Graphs 为首版前提 |
| 数据库 | Qt SQL + SQLite | 部署简单，适合本地历史数据和测试 |
| 并发 | QObject Worker + QThread | 保留事件循环，适合定时器、网络对象和 queued signal |
| 测试 | Qt Test + CTest | 可测试 QObject、信号、状态机和数据库逻辑 |
| 配置 | JSON + QStandardPaths | 配置可读，运行数据写入用户数据目录 |
| 视觉实验 | OpenCV 4 core/imgproc/videoio | 本地视频解码、图像处理和固定颜色规则检测 |

当前验证环境使用 Qt 6.2.4 和 OpenCV 4.5.4。Widgets、Network、SQL、Charts、QML、
Quick、Test 与 OpenCV `core/imgproc/videoio` 已通过实际配置和构建。当前 Ubuntu 的
Qt SerialBus 开发包缺少 `canbusutil` 和 Qt6SerialPort CMake 配置，工程仅在这种
不完整安装下通过 `cmake/ResolveQtSerialBus.cmake` 验证现有头文件/共享库并创建受限
导入目标；完整 Qt 安装仍优先使用官方 CMake 包。

### 4.1 配置事实来源

- `config/*.example.json` 只保存可读的首启示例，不是运行期配置的第二份副本。
- 首次启动创建数据库后，将示例设备、测点和报警规则导入 SQLite。
- 导入成功后，`device`、`tag` 和 `alarm_rule` 表成为运行期唯一事实来源。
- 窗口尺寸、最近选择页面等纯 UI 偏好使用 `QSettings`，不写入业务表。
- 后续启动不重复覆盖用户已经修改的设备和报警配置。

## 5. 总体架构

### 5.1 运行时组成

```text
IndustrialMonitor 进程
|
+-- UI 主线程
|   +-- MainWindow / 页面
|   +-- RealtimeTableModel / AlarmTableModel / DeviceTableModel
|   +-- ApplicationController
|   +-- DeviceSession / VisionSession 生命周期管理
|   +-- PluginManager
|
+-- 每台在线设备一个通信线程
|   +-- ModbusTcpWorker
|   +-- QModbusTcpClient
|   +-- 采集 QTimer
|
+-- 一个数据处理线程
|   +-- DataPipeline
|   +-- RollingStatistics
|   +-- AlarmEngine
|
+-- 一个数据库写线程
|   +-- StorageWorker
|   +-- SQLite 写连接
|
+-- 一个历史查询线程
|   +-- HistoryWorker
|   +-- SQLite 只读连接
|
+-- 一个视觉线程（仅 Widgets 入口按需使用）
    +-- VideoFileWorker / QTimer
    +-- cv::VideoCapture
    +-- ColorObjectDetector

IndustrialMonitor QML 进程（互斥入口）
|
+-- QmlApplicationFacade / QML 专用模型
+-- Qt Quick 页面
+-- 复用同一个 ApplicationController 与业务线程边界

动态库
|
+-- libprotocol_sdk.so
+-- plugins/libmodbus_tcp_plugin.so

VirtualPLC 进程
|
+-- 控制界面
+-- QModbusTcpServer
+-- SimulationEngine
+-- 故障注入控制
```

### 5.2 架构原则

1. UI 只展示模型和发送用户命令，不直接持有协议对象或数据库连接。
2. 协议插件只负责连接、协议读写、数据解码和通信错误，不执行报警或数据库逻辑。
3. 数据处理层只接收协议无关的测量数据，不依赖 `QModbusDataUnit`。
4. 数据库层不判断报警，不访问 UI 控件。
5. 跨线程只传递值对象，不跨线程直接调用 Worker 方法。
6. 每个 QObject 及其子对象只在所属线程中创建、使用和销毁。
7. 插件的动态库生命周期长于插件创建的全部 Worker。
8. 视觉模块不接触 Modbus、报警和 SQLite；跨线程只发送拥有独立像素的 `QImage`。
9. QML 只通过 `QmlApplicationFacade` 使用基础类型和展示模型，不持有业务 Worker。

## 7. 动态协议插件设计

### 7.1 插件接口

`IProtocolPlugin` 是不继承 QObject 的纯 C++ 工厂接口：

```cpp
class IProtocolPlugin
{
public:
    virtual ~IProtocolPlugin() = default;

    virtual ProtocolDescriptor descriptor() const = 0;
    virtual AbstractDeviceWorker* createWorker(
        const DeviceConfig& config) = 0;
};
```

接口 IID 固定为：

```text
com.muyang.IndustrialMonitor.ProtocolPlugin/1.0
```

插件类同时继承 `QObject` 和 `IProtocolPlugin`，使用 `Q_PLUGIN_METADATA` 和 `Q_INTERFACES` 导出。插件 JSON 至少包含：

```json
{
  "key": "modbus-tcp",
  "displayName": "Modbus TCP",
  "apiVersion": 1,
  "capabilities": ["read-registers", "write-register"]
}
```

### 7.2 Worker 接口

`AbstractDeviceWorker` 继承 QObject，并定义跨线程异步契约：

```cpp
class AbstractDeviceWorker : public QObject
{
    Q_OBJECT

public slots:
    virtual void start() = 0;
    virtual void stop() = 0;
    virtual void writeValue(const WriteRequest& request) = 0;

signals:
    void stateChanged(const DeviceState& state);
    void samplesReady(const SampleBatch& samples);
    void writeFinished(const WriteResult& result);
    void communicationError(const DeviceError& error);
    void transactionLogged(const TransactionLog& log);
    void stopped();
};
```

连接成功是异步事件，因此 `start()` 不返回表示连接结果的 `bool`。命令是否完成必须通过信号表达。

### 7.3 ABI 与加载约束

- `protocol_sdk` 使用 `Q_DECL_EXPORT` / `Q_DECL_IMPORT` 定义明确的共享库导出宏；主程序和插件链接同一个 SDK 目标。
- 主程序和插件必须使用同一编译器 ABI、Qt 主次版本和 `protocol_sdk` 版本构建。
- `PluginManager` 保存每个 `QPluginLoader`，不得使用局部加载器后丢失生命周期。
- 加载后必须检查 IID、`apiVersion`、插件 key 和 `qobject_cast` 结果。
- 单个插件失败只导致该协议不可用，不能阻止主程序启动。
- `createWorker()` 返回无 parent 的 Worker，由 `DeviceSession` 负责线程编排和最终销毁。
- 首版不支持运行时卸载。退出前先停止全部设备线程，再销毁插件对象和加载器。
- 插件目录固定为可执行文件同级的 `plugins/`，开发构建和安装构建使用相同相对布局。

## 8. 线程模型与生命周期

### 8.1 线程分工

| 线程 | 对象 | 说明 |
| --- | --- | --- |
| UI 主线程 | Widgets、Models、Manager、PluginManager | 仅执行轻量编排和显示更新 |
| 通信线程 | 单台设备的 Worker、QModbusTcpClient、QTimer | 每台在线设备一个线程 |
| 数据处理线程 | DataPipeline、RollingStatistics、AlarmEngine | 所有设备共享，串行处理业务数据 |
| 数据库写线程 | StorageWorker、SQLite 写连接 | 使用事务批量写入 |
| 历史查询线程 | HistoryWorker、SQLite 只读连接 | 避免历史查询阻塞实时写入和 UI |
| 视觉线程 | VideoFileWorker、VideoCapture、QTimer、检测器 | 解码和检测不阻塞 UI；仅发送值对象结果 |

首版只有一台设备时仍保留以上边界，以真实展示插件设备线程、数据处理线程和数据库连接线程亲和性。视觉线程由 `ApplicationController` 内的 `VisionSession` 管理；当前 QML 入口复用同一控制器，因此也会启动空闲视觉会话，但不暴露视觉页面或命令。不得继续拆出日志线程、告警线程或统计线程。

### 8.2 创建顺序

```text
ApplicationController 启动
-> 注册跨线程元类型
-> 启动 DataPipeline 线程
-> 启动 StorageWorker 线程
-> 启动 HistoryWorker 线程
-> PluginManager 扫描 plugins/
-> ApplicationController 根据配置创建设备会话
-> DeviceSession 创建 Worker 和 QThread
-> Worker moveToThread
-> QThread::started -> Worker::start
-> Worker 在通信线程创建 QModbusTcpClient 和 QTimer
-> ApplicationController 创建 VisionSession；视觉 Worker 在线程启动后创建 Timer/Capture
```

Worker 在主线程创建时不能创建计时器和网络子对象。它移动到目标线程后，才在 `start()` 中创建这些对象。

### 8.3 跨线程数据

以下类型是只包含值语义的 DTO，使用 `Q_DECLARE_METATYPE` 并在启动时注册：

- `DeviceConfig`
- `DeviceState`
- `MeasurementSample`
- `SampleBatch`
- `WriteRequest`
- `WriteResult`
- `DeviceError`
- `TransactionLog`
- `AlarmEvent`
- `RealtimeSnapshot`
- `VisionSourceInfo`
- `VisionFrameResult`

跨线程连接明确使用 `Qt::QueuedConnection`。接收方不得保存发送方对象指针，也不得从 UI 线程直接调用 Worker。

### 8.4 关闭顺序

```text
MainWindow 请求退出
-> ApplicationController 禁止新命令
-> VisionSession 停止播放并退出视觉线程
-> ApplicationController 请求 DeviceSession 停止轮询和断开连接
-> 等待 Worker::stopped
-> 退出并等待全部通信线程
-> 在 DataPipeline 线程设置队列栅栏，排空已投递样本后退出
-> StorageWorker 提交剩余事务、关闭数据库并退出
-> HistoryWorker 取消查询、关闭只读连接并退出
-> 销毁 PluginManager 和 QPluginLoader
-> 关闭 UI
```

所有等待均设置有限超时。超时后记录错误并继续可控退出，不无限阻塞主线程。

## 9. Modbus TCP 数据设计

### 9.1 开发连接参数

| 参数 | 默认值 |
| --- | --- |
| 主机 | `127.0.0.1` |
| 端口 | `1502` |
| Server Address / Unit ID | `1` |
| 轮询周期 | `500 ms` |
| 单次请求超时 | `800 ms` |
| Qt 协议级重试 | `1` 次 |
| 连续失败阈值 | `3` 次 |

开发环境不默认使用端口 `502`，避免 Linux 低端口权限影响演示。

### 9.2 Holding Register 映射

| Qt 起始地址 | 工业表示 | 名称 | 编码 | 权限 |
| ---: | ---: | --- | --- | --- |
| 0 | 40001 | 温度 | 有符号整数，值除以 10，单位 ℃ | 读 |
| 1 | 40002 | 压力 | 无符号整数，值除以 100，单位 MPa | 读 |
| 2 | 40003 | 电机转速 | 无符号整数，单位 rpm | 读 |
| 3 | 40004 | 电压 | 无符号整数，值除以 10，单位 V | 读 |
| 4 | 40005 | 运行状态 | 位标志 | 读 |
| 10 | 40011 | 目标转速 | 无符号整数，单位 rpm | 写 |

`40001` 是面向工程人员的文档表示，传给 `QModbusDataUnit` 的地址是 `0`。该区别必须在代码常量和 README 中明确。

运行状态位定义：

```text
bit 0: Running
bit 1: Warning
bit 2: Fault
bit 3: Maintenance
```

### 9.3 轮询过程

每次轮询使用功能码 03，一次读取地址 0 开始的 5 个 Holding Registers：

```text
QTimer::timeout
-> 检查连接状态
-> 检查 inFlight 标志
-> sendReadRequest(HoldingRegisters, 0, 5, unitId)
-> 保存请求编号和开始时间
-> QModbusReply::finished
-> 检查协议错误
-> ModbusRegisterCodec 解码
-> 发出 SampleBatch 和 TransactionLog
-> reply->deleteLater()
-> 清除 inFlight
```

如果上一次请求尚未完成，本次定时器触发只记录一次 skipped poll，不创建新请求。这样不会因设备变慢造成请求队列无限增长。

写入目标转速使用功能码 06。写入结果必须通过 `writeFinished` 返回，UI 不能在发出请求时提前显示成功。

### 9.4 通信日志边界

首版记录：

- 时间戳和设备 ID。
- TX 或 RX 方向。
- 请求编号。
- 功能码。
- 寄存器类型、起始地址和数量。
- 解码值或异常码。
- 往返耗时。
- Qt 错误码和错误文本。

该日志是逻辑事务日志，不声称是网卡抓包结果，也不伪造 Qt API 未提供的完整 MBAP 原始字节。

## 10. 连接状态机与重连

### 10.1 状态定义

```text
Stopped
   |
   | start
   v
Connecting -- connected ----------------------> Online
   |                                             |
   | connection failed                          | three consecutive failures
   v                                             v
Reconnecting -- retry timer ----------------> Connecting

Stopped / Connecting / Online / Reconnecting
   |
   | stop
   v
Stopping -> Stopped

Stopped / Connecting
   |
   | unrecoverable local configuration error
   v
Faulted -- configuration corrected ----------> Stopped
```

`Faulted` 只用于不可恢复的本地配置或插件错误，例如插件版本不兼容、地址配置非法。网络断开不进入永久 Faulted，而是进入 Reconnecting。

### 10.2 错误分类

| 类型 | 示例 | 处理 |
| --- | --- | --- |
| 配置错误 | IP 非法、地址越界 | 进入 Faulted，等待用户修改 |
| 连接错误 | 拒绝连接、服务器关闭 | 进入 Reconnecting |
| 超时 | Reply 超时 | 计入连续失败，达到阈值后重连 |
| 协议错误 | Modbus exception | 记录异常；非法地址等确定性错误不盲目重试 |
| 数据错误 | 长度不符、编码越界 | 标记 Bad，不写入正常统计 |
| 插件错误 | 加载失败、ABI 不兼容 | 禁用对应协议并展示错误 |

### 10.3 重连策略

应用级重连使用退避间隔：

```text
1 s -> 2 s -> 4 s -> 8 s -> 10 s -> 10 s ...
```

- 连接成功并完成第一次有效采集后，退避计数清零。
- 用户主动断开会取消重连计时器。
- 同一设备只允许存在一个连接尝试。
- 重连期间保留最后一个有效值，但数据质量改为 `Stale`。
- 连续失败达到阈值时生成一条通信报警；恢复采集时恢复同一条报警，不重复创建大量记录。

## 11. 数据处理与实时统计

### 11.1 数据对象

```cpp
struct MeasurementSample
{
    QString deviceId;
    QString tagId;
    quint16 rawValue;
    double engineeringValue;
    DataQuality quality;
    QDateTime timestampUtc;
    quint64 sequence;
};
```

时间统一以 UTC 写入数据库，整数字段使用 Unix epoch 毫秒，UI 按本地时区显示。`DataQuality` 取值为 `Good`、`Stale` 或 `Bad`。

### 11.2 DataPipeline 顺序

```text
SampleBatch
-> 验证设备 ID、序号和时间戳
-> 验证测点值域
-> 更新最近 60 秒滚动窗口
-> 计算 current/min/max/average
-> AlarmEngine 处理阈值
-> 生成 RealtimeSnapshot
-> 投递数据库写入批次
```

Bad 数据保留到通信日志，但不参与统计和阈值报警。Stale 数据显示在 UI 中，但不作为新样本进入滚动统计。

### 11.3 实时窗口

- 每个数值测点保存最近 120 个有效样本，对应 500 ms 采集下的 60 秒。
- 最大值、最小值和平均值均针对该滚动窗口，不表示当天或全部历史。
- 暂停按钮只暂停曲线和数字模型的可视更新。
- 暂停期间采集、报警和存储继续运行。
- 恢复后直接显示最新 60 秒窗口，不逐帧回放暂停期间的数据。

## 12. 报警系统

### 12.1 默认规则

| 测点 | 下限 | 上限 | 严重级别 | 回差 |
| --- | ---: | ---: | --- | ---: |
| 温度 | 10 ℃ | 80 ℃ | Critical | 2 ℃ |
| 压力 | 0.5 MPa | 2.0 MPa | Warning | 0.1 MPa |
| 转速 | 500 rpm | 3000 rpm | Warning | 100 rpm |
| 电压 | 210 V | 240 V | Warning | 5 V |

通信断开使用独立的 Communication/Critical 规则，不依赖测量值。

### 12.2 报警生命周期

```text
Inactive
-> Pending
-> ActiveUnacknowledged
-> ActiveAcknowledged
-> RecoveredAcknowledged
```

如果报警在确认前恢复，则状态为 `RecoveredUnacknowledged`；用户确认后结束。

- 数值连续 3 个 Good 样本越界才激活，过滤单点毛刺。
- 恢复必须连续 3 个 Good 样本进入带回差的正常区间。
- 同一设备、同一规则在活动期间只保留一个报警实例。
- 确认只改变确认状态，不改变现场报警条件。
- 恢复由数据条件触发，不能由确认按钮伪造。
- 每次激活、确认和恢复都记录时间。

### 12.3 报警事件字段

- 报警 ID。
- 设备 ID 和测点 ID。
- 规则 ID。
- 报警类型和严重级别。
- 触发值、阈值和单位。
- 激活时间、确认时间、恢复时间。
- 确认状态和确认备注。

## 13. SQLite 设计

### 13.1 数据库位置与连接

数据库文件位于 `QStandardPaths::AppDataLocation`，不写入源码目录。数据库连接遵守以下规则：

- `StorageWorker` 在线程内部创建唯一写连接。
- `HistoryWorker` 在线程内部创建唯一只读连接。
- QSqlDatabase 连接不跨线程传递。
- 启用 `PRAGMA journal_mode=WAL` 和 `PRAGMA foreign_keys=ON`。
- 写入使用预编译语句和事务批处理。
- 连接在线程退出前关闭并移除。

### 13.2 表结构

```sql
CREATE TABLE device (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    protocol_key TEXT NOT NULL,
    host TEXT NOT NULL,
    port INTEGER NOT NULL,
    unit_id INTEGER NOT NULL,
    poll_interval_ms INTEGER NOT NULL,
    timeout_ms INTEGER NOT NULL,
    protocol_retries INTEGER NOT NULL,
    failure_threshold INTEGER NOT NULL,
    enabled INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE tag (
    id TEXT PRIMARY KEY,
    device_id TEXT NOT NULL,
    name TEXT NOT NULL,
    unit TEXT NOT NULL,
    register_type INTEGER NOT NULL,
    address INTEGER NOT NULL,
    scale REAL NOT NULL,
    writable INTEGER NOT NULL DEFAULT 0,
    FOREIGN KEY(device_id) REFERENCES device(id)
);

CREATE TABLE measurement (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id TEXT NOT NULL,
    tag_id TEXT NOT NULL,
    value REAL NOT NULL,
    quality INTEGER NOT NULL,
    timestamp_utc INTEGER NOT NULL,
    sequence INTEGER NOT NULL,
    FOREIGN KEY(device_id) REFERENCES device(id),
    FOREIGN KEY(tag_id) REFERENCES tag(id)
);

CREATE TABLE alarm_rule (
    id TEXT PRIMARY KEY,
    device_id TEXT NOT NULL,
    tag_id TEXT,
    rule_type INTEGER NOT NULL,
    lower_limit REAL,
    upper_limit REAL,
    hysteresis REAL NOT NULL DEFAULT 0,
    activation_samples INTEGER NOT NULL DEFAULT 3,
    recovery_samples INTEGER NOT NULL DEFAULT 3,
    severity INTEGER NOT NULL,
    enabled INTEGER NOT NULL DEFAULT 1,
    message TEXT NOT NULL
);

CREATE TABLE alarm (
    id TEXT PRIMARY KEY,
    rule_id TEXT NOT NULL,
    device_id TEXT NOT NULL,
    tag_id TEXT,
    message TEXT NOT NULL,
    severity INTEGER NOT NULL,
    trigger_value REAL,
    activated_at_utc INTEGER NOT NULL,
    acknowledged_at_utc INTEGER,
    recovered_at_utc INTEGER,
    acknowledgement_note TEXT,
    FOREIGN KEY(rule_id) REFERENCES alarm_rule(id)
);
```

索引：

```sql
CREATE INDEX idx_measurement_device_tag_time
ON measurement(device_id, tag_id, timestamp_utc);

CREATE INDEX idx_alarm_device_time
ON alarm(device_id, activated_at_utc);
```

### 13.3 写入与保留策略

- 采集周期是 500 ms，默认每 1 秒为每个测点持久化一个最新 Good 样本。
- StorageWorker 每 1 秒或累计 50 行时提交一次事务，以先达到者为准。
- 报警激活、确认和恢复不降采样，立即进入写队列。
- 跨线程每次投递一个批次而不是逐行投递，减少事件队列压力。
- StorageWorker 保留最多 10000 行测量重试缓冲和 1000 条报警事件缓冲；达到上限时丢弃最旧测量值并产生明确的 StorageOverflow 错误，不静默增长内存。
- SQLite `busy_timeout` 默认 500 ms；写连接失败后每 2 秒尝试恢复，恢复前不阻塞 UI 或通信线程。
- 首版默认保留 7 天测量数据，启动后每天执行一次分批清理。
- 清理每批限制行数，避免长事务阻塞实时写入。
- 数据库写入失败不会覆盖实时响应；UI 显示独立的存储状态。

### 13.4 历史查询与 CSV（完整页面/导出当前未实现）

- 查询必须包含开始和结束时间，默认最近 1 小时，单次最大 24 小时。
- 查询按 `timestamp_utc` 排序并分页返回。
- 历史曲线最多渲染 5000 个点，超过时按时间桶降采样。
- CSV 使用 UTF-8，字段为本地时间、设备、测点、数值、单位和数据质量。
- 导出先写临时文件，成功后原子替换目标文件。
- 用户取消导出时删除临时文件，不留下半成品。

## 15. VirtualPLC 设计

### 15.1 模块边界

| 模块 | 职责 |
| --- | --- |
| `RegisterBank` | 保存寄存器值、范围和读写规则 |
| `SimulationEngine` | 产生可重复的温度、压力、转速和电压变化 |
| `VirtualPlcServer` | 配置 QModbusTcpServer 并同步寄存器 |
| `VirtualPlcWindow` | 展示值并发送模拟和故障命令 |

Server 保持在 VirtualPLC UI 线程，因为首版只有一个本地客户端且工作量很轻。不得为了与上位机对称而增加无必要的服务器线程。

### 15.2 正常模拟

- 每 500 ms 更新一次。
- 默认温度围绕 42 ℃ 缓慢变化。
- 默认压力围绕 1.2 MPa 缓慢变化。
- 实际转速逐步逼近目标转速，而不是瞬间跳变。
- 电压围绕 220 V 小幅变化。
- 使用固定随机种子或确定性函数，使测试和演示可复现。

### 15.3 故障注入

| 命令 | 行为 | 预期上位机表现 |
| --- | --- | --- |
| 制造高温报警 | 温度设置并保持在 86.3 ℃ | 3 个样本后产生 Critical 报警 |
| 恢复正常温度 | 温度恢复到约 42 ℃ | 满足回差和连续样本后报警恢复 |
| 断开通信 | 关闭 Modbus Server 监听和连接 | 上位机进入 Reconnecting 并产生通信报警 |
| 恢复通信 | 重新监听 1502 端口 | 上位机自动连接并恢复通信报警 |
| 冻结数据 | 停止值变化但继续响应 | 用于区分设备冻结与通信断开 |

VirtualPLC 界面只控制模拟器，不直接通知上位机制造何种结果；所有结果必须经过真实 Modbus TCP 链路出现。

## 17. 错误呈现原则

- 通信失败、数据质量异常和数据库失败是相互独立的状态。
- SQLite 写入失败不能把已经采集到的实时数据改成通信失败。
- 4 类用户可见错误分别为：插件加载、设备通信、数据处理和存储。
- 状态栏只显示最近的重要事件；详细原因进入对应页面和日志。
- 可恢复错误提供重试状态，不使用阻塞式模态对话框反复打断监控。
- 配置错误必须指出具体字段，不只显示“连接失败”。

7. 温度保持 86.3 ℃ 后产生一条 Critical 报警，恢复后更新同一报警记录。
8. 关闭 VirtualPLC 后产生一次通信报警并自动重连，恢复服务器后自动恢复采集。
9. 测量和报警数据正确写入 SQLite，数据库操作不阻塞 UI。
10. 完整历史页面和 UTF-8 CSV 导出属于后续范围，当前未实现，不作为本次验收项。
11. 所有 Worker 和数据库连接均在所属线程创建和销毁，退出时无线程遗留。
12. 单元测试和集成测试由 CTest 统一执行，核心状态机、报警和寄存器编解码均有覆盖。
13. README 中的功能描述与实际实现和测试结果一致，不写未经验证的性能结论。
14. Widgets 视觉页可打开受支持的本地视频，完成首帧、播放控制、红色目标画框计数和结束后重播；视觉错误不影响工业监控闭环。
15. QML 并行前端可复用同一业务控制器，但当前不包含视觉页面。

## 23. 面试说明边界

可以准确说明：

- 使用 Qt 动态插件隔离协议实现，并处理接口版本和插件生命周期。
- 使用 QObject Worker + QThread 保证 Modbus、计时器和 SQLite 的线程亲和性。
- 使用异步信号表达连接、读写和错误结果，而不是用同步 `bool` 假装操作已经完成。
- 使用单请求在途、超时、失败阈值和退避重连处理设备掉线。
- 使用数据质量、连续样本和回差减少误报警与报警抖动。
- 使用 SQLite WAL、独立读写连接和事务批处理保存历史数据。
- 使用 VirtualPLC 和集成测试验证采集、写入、报警、掉线和恢复的完整链路。
- 使用独立视觉线程完成本地视频解码和固定 HSV 红色目标检测，并通过深拷贝 `QImage` 保持跨线程图像所有权清晰。

不能夸大为：

- 已适配真实 PLC 厂商或复杂工业现场。
- 支持全部 Modbus 功能码和 RTU。
- 实现了原始网络抓包器。
- 经过生产级高可用或大规模设备压力验证。
- 实现了 AI/YOLO、通用目标识别、生产级视觉质检或摄像头采集。

项目价值来自可运行的闭环、清晰的所有权和可复现的异常测试，而不是功能数量。
